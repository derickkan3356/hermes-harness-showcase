# Chat context — a follow-up sees the last turn's tool results

A follow-up in an Open WebUI chat gets the previous answers as text and nothing else. The searches and page extracts behind those answers stay in `~/.hermes/state.db` and never reach the model, so any question the brief did not already answer makes the agent search again — sometimes to a worse source than the one it read a minute ago. The `.cursor/plans/frontend.plan.md` weather brief is the case: the brief gave the high, the follow-up asked for the low, and the agent re-searched and took 26 度 from a snippet that contradicted the same day's forecast.

Shape: an Open WebUI **Pipe function**, kept in this repo, that sends `X-Hermes-Session-Id: owui-<chat_id>` with each turn. Hermes then drops the request body's history and rebuilds the conversation from its own session record, tool calls and tool results included (`api_server.py`, the `provided_session_id` branch → `get_messages_as_conversation`). A Pipe is needed because a plain Open WebUI connection sends only static headers, and one static session id would merge every chat into one.

## Rejected

- Prompting the model to prefer its own transcript over a new search. Three of four follow-ups searched again with the tool results in context; the context is delivered either way and the judgement is the model's: `docs/open-webui.md` (How a chat maps to a Hermes session).
- `/v1/responses` chaining (`conversation`, `previous_response_id`) as the carrier — the stored transcript doubles every turn: `docs/open-webui.md` (Alternatives that were ruled out).

## Open

- Branches. One Hermes session per chat means edit and regenerate write both branches into one transcript, and with the Pipe that transcript is now the model's context — today the branches share a session record but no context, so this makes a hidden problem visible. `POST /api/sessions/{id}/fork` is the tool for it and works: it copies the whole transcript including tool rows into the child (`probe-fork-a`, `probe-fork-b`, 24 messages and 8 tool rows each), the same parent can be forked twice, and a parent marked `branched` still accepts turns. What is missing is truncation — `rewind_to_message` exists in `hermes_state.py` but no route exposes it, so a session cannot be forked *at* an earlier message after the fact. The design that avoids needing it is one Hermes session per assistant message, forked from the session whose tip is the new turn's parent, which turns the Pipe's map from `chat_id → session` into `message_id → session` and grows `state.db` quadratically. Its own plan, later.
- Compression rotation on the streaming path. Compression can move a session to a child id, and streaming `/v1/chat/completions` writes `X-Hermes-Session-Id` into the SSE headers before the turn runs, so the Pipe cannot learn the new id from the response. Session listings carry `parent_session_id` and `_lineage_root_id`, so the Pipe could resolve the lineage tip after each turn. Not needed yet: no `api_server` session has compressed so far — `tools/facts.sh webui` prints `api_server_child_sessions`, and the two it counts are the fork probes.
